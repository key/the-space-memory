# ADR-0018: ファイルあたりコード行数ゲート（閾値 800 + 凍結ベースラインのラチェット）

- **Deciders**: key
- **Related**:
  [ADR-0016](./0016-cognitive-complexity-gate.md)

## Context

現状のサイズ／複雑度ゲートはすべて **関数単位** である。

- lizard の cyclomatic complexity（`metrics.yml` の complexity job、CCN15 / baseline 13）
- clippy の cognitive complexity（[ADR-0016](./0016-cognitive-complexity-gate.md)、閾値 15 + 属性免除）

これらは「1 関数が複雑すぎる」ことは捕捉するが、「**1 ファイルが大きくなりすぎる**」
ことは捕捉しない。実際、コードのみ（後述）で計測したファイル行数は以下のように
偏っている。

| File | コード行数（テストmod除外） |
|---|---|
| `src/cli.rs` | 2301 |
| `src/config.rs` | 1212 |
| `src/user_dict.rs` | 953 |
| `src/main.rs` | 899 |

巨大ファイルは次の問題を生む。

1. **読解・レビュー負荷** — 1 ファイルが多責務を抱え、変更の影響範囲が見通しにくい。
2. **カバレッジの死角になりやすい** — 大きいファイルほど一括除外
   （`--ignore-filename-regex`）に逃げがちで、テストが届かない（#303 で顕在化）。
3. **関数単位ゲートのすり抜け** — 各関数は閾値内でも、ファイル全体としては肥大化する。

関数単位の複雑度ゲートを**補完**するため、ファイル単位のコード行数ゲートを導入する。

## Decision

`src/**/*.rs` の各ファイルに対し、**コード行数**の上限ゲートを CI に置く。

### コード行数の定義

ファイル先頭から、**末尾の inline テストモジュール** `#[cfg(test)] mod tests { … }` の
直前までの物理行数を「コード行数」とする。境界は「行頭（インデントなし）の
`#[cfg(test)]` のうち、直後の非空行が `mod tests` を開くものの**最後**」。末尾テスト
モジュールが無ければファイル全行。

- 除外するのは **末尾の `mod tests` ブロックのみ**。本番コード中の空行・コメントは数える。
- 末尾モジュールより前にある**テスト専用の補助項目**（`#[cfg(test)] pub fn helper()`、
  `#[cfg(test)] pub mod test_utils;` のような宣言）は本番領域にある小さなコードなので
  **コードとして数える**。除外するのは嵩む inline テスト本体だけ。

#### 境界検証

境界は proc-macro2 の字句解析（トークンスキャン）で正確に決定する（#314）。
top-level のトークン列を走査して `mod tests Group(Brace)` のアンカーを見つけ、
後ろに向かってオプショナルな可視性修飾子（`pub` / `pub(…)`）と連続する
外部属性列（`# Group(Bracket)`）を遡る。属性列のいずれかが正確に `cfg(test)`
（ident `cfg` ＋ 括弧グループ内の単一 ident `test`）であれば、そのアイテムが
マッチする。**最後の**マッチが除外領域となる。

`start_line` = 属性列先頭の `#` トークンの行番号、`end_line` = ブロック閉じ `}` の
行番号（`Group::span_close`）。raw 文字列フィクスチャ（`r#"…"#` の中身は任意の
col-0 行を含みうる）はトークナイザが単一リテラルとして扱うため、内部を走査する
必要がない。

末尾モジュールより**後ろ**にある本番コードも計数される（以前の行ベースの
ヒューリスティックでは検出が不完全だったが、#314 で解決済み）。

**境界分離の fail-closed**: 除外領域の境界行をトップレベルの本番トークンが
共有する場合（例: `fn a() {} #[cfg(test)]` が 1 行）はエラーとして止める。
より広い述語（`cfg(all(test,…))`）や `cfg_attr(…, cfg(test))` は対象外とし、
本番コードとして計数する（過剰計数 → ゲートが鳴る方向で fail-noisy）。

### 閾値とラチェット

| 要素 | 値 |
|---|---|
| 基本閾値 | コード 800 行 |
| 既存の超過ファイル | **凍結ベースラインのラチェット** |

チェックインした**ベースラインファイル**に、現時点で 800 を超えるファイルの
コード行数を凍結記録する。ゲートは以下の **3 つの不変条件**を CI で強制する。
`max(800, baseline)` の単純比較だけでは「ファイルと baseline を同時に増やす差分」が
通ってしまい、ラチェットが reviewer 規律に留まる。ゲートを CI 不変条件にするには
baseline ファイル自体の変化も検査する必要がある。

各ファイル F のコード行数を C、ベースライン値を `baseline[F]`（無ければ未登録）とする。

1. **成長禁止**: `C > max(800, baseline[F])` なら fail。新規ファイル（未登録）は
   `max(800, なし) = 800` が上限。
2. **tightness（陳腐化防止）**: `baseline[F]` が登録されているなら、
   `baseline[F] == C` かつ `baseline[F] > 800` であること。`C < baseline[F]` なら
   「baseline を C に引き下げよ」、`C <= 800` なら「baseline から削除せよ」と fail。
   stale な高 baseline が残って後の再増殖を許す穴を塞ぐ。
3. **不変性（反インフレ＝ラチェット本体）**: base branch（`origin/main`）と比較し、
   baseline 値の**増加を許さない**。baseline を引き上げる差分は fail。これにより
   「ファイルと baseline を同時に増やせば通る」抜け道を塞ぎ、「既存ファイルは増やせない」
   を reviewer 規律ではなく CI 不変条件にする。

新規ファイルが 800 を超える場合: (1) で fail。baseline を新規追加して回避しようと
しても、(3) が base に対する `0 → C` の増加として fail させる。したがって新規ファイルは
確実に 800 以下に保たれる。

ファイルを分割・縮小したら、ベースラインを新しい値に**引き下げ**（(2) が強制）、
800 以下になれば**削除**する。ベースラインは決して引き上げられない（(3)）。

不変性 (3) は専用の `file-lines` ジョブ（`origin/main` を fetch 済み）で**権威的**に
判定し、そこでは base が解決できない場合 **fail-closed**（pass せずエラー）にする。
base の baseline が読めても読めなくても黙って通すと、CI 設定ミスでラチェットが無効化
されるため。なお `origin/main` に baseline ファイルが**まだ無い**状態（本ゲートを main に
入れる導入 PR）は bootstrap として (3) をスキップする。これは導入 PR 限定の窓で、
**マージ後に main 上へ baseline が乗った時点で (3) は初発火**して以降常時有効になる。

初期ベースライン（実値はベースラインファイルが権威）: `cli.rs` 2301 /
`config.rs` 1212 / `user_dict.rs` 953 / `main.rs` 899。

### 違反メッセージ

ゲートはファイル単位で「path・現在のコード行数・適用上限（800 または baseline）」を
明示して落とす。どのファイルが何行で上限いくつかが一読で分かること。

## Rationale

**なぜコードのみ（テスト除外）か。**
テストは網羅的であるほど長くなり、それ自体は健全である。テスト行数で本番ファイルを
罰するとテストの充実を抑制する（アンチゴール）。ゲートが対象とするのは本番コードの
肥大化なので、テストモジュールは数えない。実際 `cli.rs` は 3617 → 2301、`indexer/mod.rs`
や `synonyms.rs` はテスト込みでは 800 超だがコードのみでは 800 未満に収まり、
ベースライン不要になる。

**なぜ「物理行数 − テストmod」で、空行・コメントも数えるか。**
tokei / cloc のような「空行・コメントを除く厳密 LOC」はパーサ／ツール依存を増やし、
定義も不透明になる。本ゲートの目的はファイルの**規模・見通しやすさ**であり、物理行数で
十分な代理になる。除外を「テストmod のみ」に絞ることで、規則の透明さを優先する。

**なぜ閾値 800 か。**
現在のコードのみ分布で 800 を超えるのは 4 ファイルのみ。日常的に書くファイルには
当たらず、明確に肥大化したものだけを捕捉する水準として 800 を置く。関数単位ゲートの
15 のような「覚えやすい丸い値」で、初期導入の摩擦を抑える。

**なぜ凍結ベースラインのラチェットか（フラット 800 のハード fail ではなく）。**
今ある 4 つの超過ファイルをいきなりハード fail にすると、ゲートを入れる前に巨大ファイル
分割という大規模リファクタが必要になり、**ゲート導入がリファクタにブロックされる**。
凍結ベースラインなら、ゲートを**今**入れて「これ以上太らせない」を即日効かせつつ、
分割は段階的に進められる（#303 の `cli.rs` 分割などでベースラインが自然に下がる）。
lizard の baseline カウントと同じ発想だが、**per-file かつ値がファイルに明示**される点で
透明性が高い。

**なぜ base branch（origin/main）との比較が要るか。**
ベースラインファイルはチェックイン済みで PR から編集できる。「ベースラインが
引き上げられていない」ことは現在のツリーだけでは判定できず、**履歴（base branch）との
比較でしか検証できない**。比較を省くと、ファイルと baseline を同時に増やす差分が通り、
ラチェットは CI 不変条件ではなく reviewer 規律に退化する（Codex 指摘の核心）。CI は
full clone を持つため `origin/main` 版のベースラインを参照できる。

**なぜ fail-closed のテストストリップか。なぜ字句解析を使うか。**
行ベースのヒューリスティック（最後の col-0 `#[cfg(test)]` を境界とし、EOF が col-0
`}` であることを確認）では、`mod tests` の後ろに col-0 `}` で終わる本番アイテムを
置くと検出できなかった。また、内部をブレース深度で走査すると raw 文字列
フィクスチャ内の col-0 `}` を誤検知する問題があった。

proc-macro2 による字句解析はこれら両方を解決する。raw 文字列はトークナイザが
単一リテラルとして扱うため内部走査が不要になり、`mod tests` の後ろの本番コードも
スパン情報から正確に検出できる。透明性の根拠は「grep 一発で再現できる規則」から
「字句的に厳密なトークンスキャン」に移行した。境界分離チェック（境界行の共有で
エラー）により、あいまいなレイアウトは黙って通さない。

検討した代替案と却下理由:

- **ゲートを置かない**: 巨大ファイルが無制限に育つ現状を放置する。却下。
- **フラット 800 のハード fail（ベースラインなし）**: 既存 4 ファイルの分割が完了するまで
  ゲートを入れられない。導入を大規模リファクタに結合させる。却下。
- **テスト込みで数える**: テストの充実を罰し、テスト分離（#303）の動機と相反する。却下。
- **空行・コメントを除く厳密 LOC（tokei/cloc）**: ツール依存と定義の不透明さを増やす。
  規模ゲートには物理行数で十分。却下。
- **関数単位のみ（既存ゲート）**: ファイル全体の肥大化を捕捉できない。本ゲートで補完。

## Consequences

### Positive

- ファイルの無制限な肥大化を止め、巨大ファイルの分割を促す。分割は #303 の
  カバレッジ向上（小さいファイルほどゲート対象化しやすい）と相乗する。
- ベースラインファイルが「肥大化負債の単一観測点」になり、各負債の現在値が
  ファイルに明示され grep 可能（ADR-0016 の `#[allow]` 一覧と同じ思想）。
- ラチェットによりゲートを即日導入でき、リファクタにブロックされない。

### Negative

- 物理行数は粗い指標。800 直下の高密度ファイルと 800 超の低密度ファイルを同等に
  扱えない（規模の近似と割り切る）。
- ストリップ規則は top-level の `#[cfg(test)] mod tests { … }` を字句的に検出する。
  `cfg(all(test,…))` や `cfg_attr(…, cfg(test))` でガードされたテストモジュールは
  検出されず、本番コードとして計数される（過剰計数方向で fail-noisy）。
- ベースラインファイルという保守対象が増える。tightness 不変条件により、baselined
  ファイルの行数が変わるたびベースライン更新が要る（ゲートが新値を提示するので機械的だが、
  並行 PR でベースライン行の merge conflict が起きうる摩擦がある）。縮小を可視化・追跡
  できる利点と表裏。
- ラチェットの不変性チェックは base branch（`origin/main`）の参照を要する。純粋な単体
  テストだけでは完結せず、CI で git の base 参照を行う実装が必要になる。
- 800 は現分布に合わせた較正値で、絶対的根拠はない（将来の再調整を許容する）。

### Scope（対象外）

- `src/` 以外（`tests/`・`benches/`・`build.rs` 等）。
- 関数単位のメトリクス（lizard / ADR-0016 が担当）。
- 厳密 LOC・トークン数・空行/コメント除外。
